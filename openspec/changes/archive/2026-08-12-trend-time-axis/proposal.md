# Proposal: 趨勢圖時間軸與區間選擇

## Why

回報趨勢頁的體重、血壓、步數沒有年月選擇，資料多年後會很擠。
2026-08-12 實讀程式碼並查詢生產庫核對後，確認擁擠是表象，
底下有一個更嚴重的正確性問題。

### 一、x 軸依日期索引而非時間比例（會誤讀，優先於擁擠）

`LineChart` 的 x 座標是
`PL + dates.indexOf(d) * (寬度 / (dates.length - 1))`
（app/src/viewer/assets/app.js:79），即第 n 個有資料的日期就畫在第 n
個位置，與該日期距離前後點的實際時間長短無關。後果是時間間隔全被
壓平：

- 生產庫實測有一條已停止記錄的序列，末筆**距今數百天**，但它畫在圖的
  最右端，看起來像是最新的量測，讀圖的人會誤以為是近期數據。
- 檢驗趨勢受影響最大：相隔兩天與相隔一年的兩次檢驗，在圖上距離
  相同，趨勢斜率因此失真。

同一個檔案裡的 `DispenseTimeline` 已經用時間比例
（`(t - t0) / (t1 - t0)`，app.js:114），也就是 `LineChart` 是不一致
的那一個，不是全域慣例如此。

### 二、無時間區間選擇，密集序列嚴重過度重疊

趨勢頁的體重與血壓是全量直接畫（總覽頁的體重圖有 `slice(-365)`，
那是「最後 365 筆」而非「最近 365 天」，趨勢頁則完全沒有切片）。生產庫的密集序列實際會畫**千點量級**，繪圖區寬 712px，
等於每點 0.42px，遠低於單一標記所需寬度。步數之所以看起來還好，
是因為它先做了月平均（`monthlyAvg`）壓成約 50 點，不是原始逐日。

即將到來的 CPAP 資料會讓這件事惡化：每日 AHI 數百點（每點約 1.5px），
Phase 2 帶進四年逐日約 1400 點（每點 0.51px），而且會新增四張以上
圖表。

### 三、O(n²) 效能

`dates.indexOf(d)` 寫在 `series.map` 內部，每點都線性搜尋整個日期
陣列。千點量級約數百萬次比較，目前尚可；點數再成長會開始拖慢渲染。

### 為何排在 CPAP 之前

本 change 不動 schema、不碰匯入，範圍只在檢視層，改完 CPAP 的新圖
直接建在修好的基礎上，而不是先繼承缺陷再回頭改七張圖。使用者
2026-08-12 裁示採此順序。

## What Changes

- **`LineChart` x 軸改為時間比例**：以實際日期在區間內的位置定位，
  時間空窗如實呈現。五個呼叫點（總覽體重、趨勢檢驗／體重／血壓／
  步數）全部受益，且與同檔的 `DispenseTimeline` 語意一致。
- **時間區間選擇**：趨勢頁一組作用於全頁的區間按鈕（近三月／近一年／
  全部）＋依資料新舊自動預設；單圖在區間內無資料時顯示無資料訊息與
  「看全部」入口。
- **x 軸刻度改按時間挑、末點標籤改右側圖例**：原型實測證實不改會分別
  造成刻度重疊與標籤被右邊界截斷。
- **密集序列標記兩段降級**：依標記直徑推導門檻，超過即只畫折線不畫
  標記（原型實測 SVG 節點降逾九成，視覺幾乎無變化）。
- **日期健全性**：null 與無法解析的日期在繪製前剔除並標示筆數
  （`new Date(null)` 為 1970，單一筆即可無聲毀掉整張圖）。
- **匯出 HTML 同步受益**：檢視器與匯出共用同一份 `app.js`，天生同步
  （既有資產防漂移測試會強制 `src/dashboard/app.js` 同步更新）。

### 明確排除（2026-08-12 原型實測後收斂）

- **不做時間桶聚合**。原型量得：聚合的可讀性收益接近零（只畫線的
  廉價版視覺上與保留標記幾乎相同），其真實收益是折線頂點數大幅降至
  約 237，屬效能而非可讀性，而目前渲染無可感知延遲。聚合規則本身也
  待資料到齊再定（AHI 這類指標的單一壞夜有臨床意義，取中位數會抹掉；
  體重取中位數無妨），且會引入成對序列拆散配對、混合序列圖說語意、
  末桶與最新值位置矛盾三個未解問題。延後至單日多次量測或逐分鐘序列
  進入資料庫後再評估，並以已知限制寫進 spec。
- **不新增資產模組**。不做聚合後新增的純邏輯只有五個小函式，且
  `app.js` 為 IIFE 無法 import；改以既有 vm sandbox 斷言渲染結果，
  不為可測性而拆檔並連動五處資產同步。
- 不動 schema、不動匯入引擎、不新增資料來源。
- 不改 `DispenseTimeline`（已是時間比例）。
- **不動總覽頁體重卡的 `slice(-365)`**（那是「最後 365 筆」而非
  「最近 365 天」，改動屬行為變更，與本 change 的正確性目標無關）。
- **不動步數的 `monthlyAvg`**（其輸出的 `"YYYY-MM"` 在時間軸下正確
  定位到月初，原型已驗證）。
- 不做互動縮放與拖曳平移。

## Impact

- **Specs**：`app-viewer` delta（共用時間域定位、區間選擇、標記降級、
  日期健全性四個新 requirement，並修訂既有互動不退化與單檔匯出兩項）；
  `dashboard-generator` delta（同一份前端資產也是 Python `mhb rebuild`
  的產物前端，趨勢圖語意變更同屬該 capability）。
- **程式**：`app/src/viewer/assets/app.js` 與必須同步的
  `src/dashboard/app.js`；可能觸及 `style.css` 兩份（區間選擇控制項
  樣式），手機版斷點需一併確認。
- **測試**：全部走既有 `app/tests/ui/viewer_render.test.mjs` 的最小
  DOM shim（vm sandbox）斷言渲染結果——座標、標記數、標籤位置、刻度
  數與圖說文字；不新增資產模組，故無獨立的純函式單元測試。
- **風險低**：純檢視層，無資料寫入路徑，錯了不會損毀資料庫。

## 決定紀錄

design 三項原始待決與 G1 複審後的範圍收斂皆已定案，無未解問題：

1. x 軸語意＝共用時間域的線性映射（時間域由區間日曆邊界決定，
   `today` 取 `meta.generated_at`）。
2. 區間選擇＝整頁一組按鈕＋自動預設＋單圖空狀態「看全部」入口
   （點擊切換整頁，維持同期對照不變式）。
3. 密集序列＝標記兩段門檻降級，不做時間桶聚合（理由見「明確排除」）。
