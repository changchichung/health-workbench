# Design: 誤歸屬救援

## 背景事實（2026-08-10 程式碼實讀，common-ground #43-#47）

- `source_documents.sha256` 全庫 UNIQUE；registerSource 命中即回傳
  原 doc（含原歸屬成員），檔層不重匯。
- 各資料表以 `doc_id` 指回 source_documents；指紋表去重鍵
  `UNIQUE(profile_id, section, record_fp)`，重複紀錄保留首見 doc
  的 doc_id，不記錄「後續哪些檔案也含有此紀錄」。
- medications 僅在母 encounter 判定 "inserted" 時寫入
  （nhi_json.js：duplicate encounter 整組用藥跳過），故 medications
  的 encounter_id 必指向同 doc 的 encounter。
- encounter 的 record_fp 以整筆來源紀錄計算（含 `r*_1` 用藥子
  陣列）：兩筆 encounter 指紋相同即代表用藥內容也相同。
- 健保 masked_id 首匯即綁定（nhi_json.js:111）；一個 masked_id
  至多綁一個成員（nhi_json.js:103 阻擋）；每次健保匯入都經護欄
  驗證，故任一成員名下全部健保 doc 必與其綁定的 masked_id 一致
  （下稱「綁定一致不變量」）。
- deleteProfile 已示範交易模式：單一交易逐表刪、中斷回滾、sha256
  釋放（engine/profiles.js:83，含測試）。

## D1: 救援原語的實作層次

1. **doc 級 DML 原語（推薦）**：新模組 `engine/doc_rescue.js`
   提供 preview / delete / reattribute 三函式，全部純 DML 單一
   交易，複用 deleteProfile 的交易模式。
   - 優點：零 DDL、爆炸半徑限定單一 doc、可獨立單元測試、UI 只是
     薄殼。
   - 缺點：改歸屬的合併語意須自行實作（見 D3）。
2. **重放式救援**：刪除 doc 後要求使用者重新匯入原始檔給正確
   成員，App 只提供刪除。
   - 缺點：原始檔已刪即無解，正是 L-4 要堵的洞；已由決定排除
     單做刪除的方案。
3. **墓碑標記**：不實刪，加 `revoked` 欄位並全查詢過濾。
   - 缺點：需 DDL、每條查詢路徑都要記得過濾（漏一處即資料外漏到
     錯的成員檢視）、sha256 不釋放需另設例外。否決。

採 1。

## D2: 去重共用紀錄的風險防護（刪除與改歸屬皆適用）

doc X 名下的紀錄可能同時存在於同成員其他檔案 Y（Y 匯入時被去重
跳過、掛在 X 名下）。刪除 X 會連帶刪掉 Y 也含有的紀錄；改歸屬
把 X 搬走同樣會使來源成員失去這些紀錄。兩者都無法以重匯 Y 回補
（Y 檔層 sha256 已登記）。DB 未記錄紀錄級多重歸屬，無法精確
判定哪些列受影響，故刪除與改歸屬的預覽 MUST 同用此警告。

1. **精確追蹤**：新表記錄每次匯入「跳過的重複紀錄指向誰」。
   - 缺點：DDL＋Python schema 同步＋回填歷史資料不可能（資訊已
     丟失）。否決。
2. **import_stats 啟發式警告（推薦）**：source_documents.
   import_stats 已記錄每檔各表 skipped_dup 筆數。預覽時檢查：
   同成員、同來源家族（adapter 前綴 `nhi_` 一族、`apple_health`
   一族）的其他 doc 中，任一 import_stats 的 skipped_dup 任表
   大於 0，即顯示重疊警告（說明刪除可能連帶移除其他檔案也含有
   的紀錄、且無法重匯回補），但不阻擋。
   - 理由：誤歸屬救援的主情境（別人的檔匯錯人）紀錄內容跨人不
     重疊，警告不會誤傷主流程；同人多檔重疊（每月健保下載、
     Apple 累積全量匯出）則必然有 skipped_dup 訊號，靈敏度足夠。
   - 已知限制：啟發式為 doc 級非紀錄級，可能過度警告（skipped_dup
     指向的是第三個 doc 而非 X）；接受，警告文案用「可能」。
3. **不警告，僅文件說明**：把語意寫進 spec 與 README。
   - 缺點：使用者在 UI 看不到，等於沒防線。否決。

採 2。

## D3: 改歸屬的衝突合併語意

把 doc X 從成員 B 搬到成員 A 時，A 名下可能已有相同紀錄
（同 section＋record_fp，或 apple 表同去重鍵）。

1. **有衝突即整批阻擋**：要求先人工清掉衝突。
   - 缺點：使用者無工具清單筆紀錄，等於死路。否決。
2. **合併（推薦）**：鏡像匯入去重規則。同一交易內逐表處理：
   - 指紋表：來源列 (section, record_fp) 已存在於目標成員者，
     刪「來源列」保留「目標列」；其中 canonical 不同者（指紋
     碰撞）比照匯入語意在目標列補 `fingerprint_collision` 旗標。
     encounters 合併＝先刪「來源 encounter」名下的 medications，
     再刪來源 encounter 本身；目標 encounter 與其自己的用藥完整
     保留（encounter 指紋含用藥子陣列，指紋同即用藥同，不丟
     資訊）。
   - apple_records / apple_workouts：按各自 UNIQUE 鍵判重，重複
     刪來源列。
   - 其餘列 UPDATE profile_id 改掛目標（medications 隨母
     encounter 一併改）。
   - source_documents.profile_id 最後改掛。
   - 預覽面板顯示「搬移 N 筆、與目標重複合併 M 筆」（M 可於預覽
     時精確計算：EXISTS 目標同鍵）。
3. **覆蓋目標**：來源列蓋掉目標同鍵列。
   - 缺點：目標列可能掛在目標自己的 doc 上，覆蓋會打斷目標的
     來源追溯，且與匯入「先到先贏」語意相反。否決。

採 2。

## D4: 健保身分綁定守恆

依「綁定一致不變量」（背景事實）：成員名下全部健保 doc 與其綁定
一致；masked_id 全庫唯一歸屬。doc 本身未存 masked_id（檔頭層
資訊，入庫即丟），規則只能建立在不變量上。

1. **健保 doc 禁止改歸屬**（只能刪＋重匯）。
   - 缺點：原始檔已刪的健保誤匯救不了；決定範圍含改歸屬。否決。
2. **不變量規則（推薦）**：
   - 改歸屬護欄：健保 doc（adapter 前綴 `nhi_`）改歸屬僅允許
     目標成員 masked_id 為空。目標已綁定者必與來源綁定不同
     （唯一性），表示檔案身分與目標不符，阻擋並說明。
   - 綁定轉移：改歸屬後來源成員名下已無健保 doc 時，同交易內
     解綁來源並將其原 masked_id 轉綁目標；來源仍有健保 doc 則
     維持來源綁定、目標暫不綁（下次健保匯入時由既有護欄補綁）。
   - 刪除解綁：刪除健保 doc 後來源成員名下已無健保 doc 時，
     同交易內解綁（決定 #51）。
   - 正確性論證：若成員被誤匯（綁定來自別人的檔），其名下健保
     doc 必全是同一誤匯身分（護欄擋掉不一致者），逐份搬走，最後
     一份離開時綁定隨之轉移，終態正確；中間態（目標持 doc 未綁）
     等價於今日「新成員首匯前」狀態，無新風險。
3. **自由搬移不管綁定**：
   - 缺點：救援後錯的綁定留在原成員，正主檔案續被擋（L-4 只堵
     一半）；且可造出「A 綁 X 卻持有 Y 身分的 doc」破壞不變量。
     否決。

採 2。

## D5: UI 形態

1. **匯入紀錄卡列內操作（推薦）**：history.js 每筆 doc 列尾加
   「刪除」「改歸屬」鈕；點擊開預覽確認面板（檔名、匯入時間、
   各表筆數、D2 警告、D3 合併筆數、D4 判定；改歸屬含目標成員
   下拉，排除現歸屬成員）；確認執行後刷新匯入紀錄卡，若影響
   當前檢視成員同步刷新檢視頁（複用成員切換的刷新路徑），成功
   與失敗均以既有暫時通知列上浮。
   - 理由：匯入紀錄卡已是全庫管理視角、依成員分組（v0.4.0
     design D3），救援語意天然落位；零新頁面。
2. **獨立救援精靈頁**：專頁列出全部 doc 與批次操作。
   - 缺點：低頻操作開專頁過重；批次救援已明確排除。否決。

採 1。確認等級依決定 #52：明細預覽＋一般二次確認（單鈕確認，
非名稱輸入級）。

## D6: 驗證策略

- 單元測試（`app/tests/engine/doc_rescue.test.mjs`）：
  - 刪除：連帶各表清除、sha256 釋放後同檔可重匯給他人、中斷
    （sabotaged driver）整批回滾、他成員資料 before/after dump
    逐位元組不變。
  - 改歸屬：全搬（目標無衝突）、合併（目標有同指紋紀錄：來源列
    消失、目標列與其用藥保留、碰撞旗標補記）、apple 表同鍵合併、
    中斷回滾。
  - 綁定守恆：健保 doc 搬到已綁定目標被阻擋零寫入；最後一份
    健保 doc 搬走時來源解綁＋目標轉綁；刪除最後一份健保 doc
    解綁；來源仍有健保 doc 時綁定不動。
  - 預覽：各表筆數、合併筆數、重疊警告觸發與不觸發（同成員同
    家族他 doc skipped_dup 有無）。
- D7 紅隊 harness 擴充（nondestructive.test.mjs）：刪除與改歸屬
  中途失敗兩情境，斷言全庫 dump 與操作前完全一致。
- UI 純函式測試：預覽面板資料組裝函式直測（沿 history_grouping
  模式）。
- 回歸：既有 100 node:test 全綠（2026-08-10 當日實測基準）；
  schema parity、匯入 parity fixture 全集不動。

## Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| 重疊啟發式過度警告（skipped_dup 指向第三個 doc 而非本 doc） | 中 | 接受：警告文案用「可能」、不阻擋（D2 已知限制）；tasks 0.1 觸發與不觸發矩陣測試 |
| 預覽與執行之間資料庫狀態改變（如另一筆匯入完成） | 低（單機單使用者） | 執行函式不信任預覽數字：前置檢查與合併判定全部在執行交易內重算（tasks 0.2/0.3） |
| App 端 rusqlite 橋未開 FK pragma，刪序錯誤不會被 DB 擋下 | 中 | 刪除順序明定（medications 先於母表）＋全庫 dump diff 斷言（tasks 0.2/0.4）；FK pragma 對齊維持既有 backlog |
| 使用者誤觸刪除造成非預期資料遺失 | 低 | 明細預覽＋二次確認（決定 #52，tasks 1.1）；D7 中斷情境保證無半刪狀態（tasks 0.4） |
