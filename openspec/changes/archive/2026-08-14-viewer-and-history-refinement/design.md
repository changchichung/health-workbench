# Design: 檢視層用語中性化、呼吸事件聚合與匯入紀錄批次摺疊

## Context

三組改動全在檢視層與匯入紀錄的呈現，不動 schema、不動 `cpap_events` 的
內容。唯一動到寫入路徑的是 `imported_at`（見 D2），而那是修既有隱患。

實測基準（2026-08-13，對生產庫副本）：

| 量 | 值 |
|---|---|
| payload 總大小 | 0.47 MB（`assemble.js` 上限 10 MB） |
| `cpap_events` 逐筆 | **110 bytes/筆**（上限推算依據） |
| `event_daily` 聚合 | 49 筆＝2.7 KB（56 bytes/筆） |
| 有逐筆事件的晚數 | 只佔有摘要晚數的一小部分（SD 卡 DATALOG 只留最近約 20 天） |
| 有事件的晚：每晚筆數 | 平均十餘，最多數十 |
| AHI | 平均 3.17，最高 17.3 |

## Decisions

### D1：四對孿生實作的同步紀律

本 change 會動到四對必須語意一致的實作。任何一對漏改都不會產生錯誤，
只會讓兩條路徑靜默分歧。

| 孿生對 | 本 change 要動的部分 | 既有守衛 |
|--------|---------------------|---------|
| `app/src/provider/payload.js` ↔ `src/dashboard/embed.py` | 事件上限語意（D3） | `provider 同構` 測試比對兩邊 payload 數值全等（apply 時實測：只改 JS 就轉紅），但**有盲區**：常數值分歧只在資料量觸及較小的那個上限時才顯現，fixture 遠低於上限故不會紅 |
| `app/src/viewer/assets/app.js` ↔ `src/dashboard/app.js` | 用語（組 1）、事件呈現（組 2） | `forbidden_guard.test.mjs` 的雙份同步守衛 |
| `app/src/knowledge/forbidden.js` ↔ `src/knowledge/forbidden.py` | 新增兩個禁用詞 | 測試解析 Python SSOT 比對 JS |
| `app/src/engine/store.js` ↔ `src/store/db.py` | `imported_at` 統一寫入（D2） | parity 測試（比對匯入結果全表） |

**方案 A（採用）**：沿用既有紀律，每組 task 完成時逐對確認，並為第一對
的**盲區**補一條常數比對守衛：解析 `embed.py` 取出兩個常數，斷言與
`payload.js` 的導出常數同值，另加「有解析到兩個常數」的護欄（擋兩邊同時
改名導致 `undefined === undefined` 的假綠）。已落地為
`app/tests/provider/cpap_event_limit_parity.test.mjs`，兩次突變（常數值
分歧／常數改名）皆轉紅。
**方案 B**：把上限常數抽到共用 JSON 由兩邊讀取。乾淨但 `embed.py` 與
`payload.js` 目前沒有共讀設定檔的機制，為一個常數建立這條管線不划算。
**方案 C**：不補守衛，靠註解。這正是本輪走查抓到「四處補了第五處沒補」
的成因，不再重複。

### D2：`imported_at` 統一寫入的實作點

現況 `registerSource()` 與 Python `db.py` 的 INSERT 都不帶 `imported_at`，
走 schema 預設 `datetime('now')`，**每列各自取當下時間**。

**方案 A（採用）**：`registerSource()` 新增 `importedAt` 參數並寫入
INSERT；多檔 adapter 在 `importSourceSet()` 開頭算一次時間戳，整批共用；
單檔 adapter 各自傳入當下時間（一批一檔，語意等價）。Python `db.py`
同步。
- 代價：三個 JS adapter 呼叫端與 Python 對應處都要改（機械改動）。
- 好處：不動 schema；批次判定 key 從「碰巧相同」變成「刻意寫入」。

**方案 B**：新增 `batch_id` 欄位（schema v5 遷移）。語意最乾淨，批次成為
第一級概念。但要在剛完成 v4 遷移的生產庫上再做一次遷移，且既有 43 列要
回填。已於 2026-08-13 裁定不採用。

**方案 C**：檢視層用「時間差在 N 秒內」的啟發式。不動寫入路徑，但分隔
閾值兩側的誤判都沒有錯誤訊息，且將來很難除錯。否決。

**殘餘風險（明列）**：兩批不同資料夾在同一秒匯入會被誤合併為一批。需要
使用者手動操作兩次匯入且落在同一秒，實務上不可能；且後果僅為顯示分組，
不影響資料。

### D3：事件上限語意與晚數選擇

語意從「最近 N **筆**」改為「最近 N **晚**的完整逐筆」。

N 的取值用實測密度推算（每筆 110 bytes）：

| N 晚 | 本機密度（十餘筆/晚） | 最壞情況（59 筆/晚） | 佔 10 MB 上限 |
|------|----------------------|---------------------|--------------|
| 30 | 504 筆＝55 KB | 1,770 筆＝190 KB | 1.9% |
| **90** | 1,512 筆＝163 KB | 5,310 筆＝571 KB | **5.7%** |
| 180 | 3,024 筆＝325 KB | 10,620 筆＝1.14 MB | 11.4% |

**方案 A（採用）**：**90 晚 ＋ 總筆數硬上限 8,000**（雙保險）。超過筆數
上限時**從最舊的晚整晚剔除**，維持「任一晚要嘛完整、要嘛不在 payload」。
- 90 晚約三個月，涵蓋一般回診間隔；最壞情況 571 KB 仍只佔上限 5.7%。
- 硬上限防的是 AHI 極高（每晚上百筆）的極端使用者：只有晚數上限時
  90 晚可能達 1.5 萬筆／1.6 MB。
**方案 B**：只設晚數上限。少一個參數，但極端情況無界。
**方案 C**：全部逐筆都帶。50,000 筆＝5.26 MB，加上其他區塊會逼近 10 MB
硬上限，而 `assemble.js` 超限即失敗。否決。

被剔除的晚數 MUST 在使用者可見處揭露（沿用 `cpap-therapy` 的「已知限制
的揭露」），文案指出「逐筆僅保留最近 N 晚，較早的晚仍有每日摘要與每晚
事件數」。

### D4：逐筆事件的定位方式

**方案 A（採用）**：**每晚一個摺疊小節**。「每晚事件數」圖下方列出有事件
的晚（日期＋該晚筆數），點一晚展開該晚完整逐筆。
- 與既有 `groupSources` 的 `<details>` 摺疊手法一致，無新互動概念。
- 純 HTML 摺疊，不需狀態管理；viewer 與 dashboard 兩份實作都容易對齊。
- 沒有事件的晚不列出（本機實測只有少數晚有），清單長度等於「有事件的
  晚數」而非總晚數。
**方案 B**：日期下拉選單選一晚。省版面，但要多一次點擊才知道哪些晚有
事件，而「哪幾晚有事件」本身是資訊。
**方案 C**：點「每晚事件數」圖上的點展開。互動最直覺，但圖上的點在密集
區間會難以命中（既有「密集序列的標記降級」requirement 已處理過同類問題），
且需要圖表元件回傳點擊事件，改動面大。

### D5：批次操作與單檔操作的並存

**方案 A（採用）**：批次列提供「改歸屬」「剔除整批」；**逐檔操作保留在
展開後的逐檔列**。
- 逐檔刪除仍有正當用途：某一檔解析錯誤要單獨移除重匯。
- 實作上批次版包住既有單檔邏輯（見「批次操作的實作形狀」），不需重寫。
**方案 B**：只留批次操作。介面最單純，但失去單檔補救能力。
**方案 C**：只在單檔層操作，批次列純顯示。摺疊後要刪整批得展開點 41 次，
等於沒解決問題。

### D6：每晚事件數的圖形

**方案 A（採用）**：折線，每個事件類型一條（阻塞／中樞／低通氣／未分類），
與既有 AHI 分項圖的呈現一致，共用 `LineChart` 與同一組色票。
- 單位一致（都是「筆數」），不觸犯 D10 那條「單一 y 軸不得混不同數量級」
  的既有紀律。
**方案 B**：堆疊條圖。總量易讀，但要新寫堆疊元件，且既有圖表都是折線，
風格不一致。

### D7：App 端摺疊邏輯的位置與守衛

viewer 的 `app.js` 是自包含嵌進單檔 HTML 的，**不能 import 外部模組**，
所以摺疊邏輯註定兩份。

**先確認過的事實**：`app/src/viewer/assets/app.js` 整份包在
`(function () { "use strict"; … })()` 裡，`groupSources` 是 IIFE 內的區域
函式，**沙箱外取不到**。因此「直接呼叫兩份函式比對回傳值」不可行。

**方案 A（採用）**：**共用測試向量**。在測試 helper 定義一組刻意設計的
來源列（同批多檔、不同批同 adapter、單檔批次、跨成員），以及期望的分組
結果；App 端直接餵給 `groupDocsByBatch()` 斷言，viewer 端把同一組資料塞進
payload 的 `meta.sources`，用既有 vm sandbox 真渲染後斷言 DOM 的分組列數
與展開內容相符。兩邊對同一向量斷言同一語意。
- 可行性已驗證：`sleep_render.test.mjs` 既有的「匯入紀錄摺疊」測試正是
  用 vm sandbox 真渲染檢查 DOM，同一手法可用。
**方案 B**：只斷言 App 端，viewer 端靠它既有的摺疊測試。少一份機制，但
兩處的分組規則將來會各自漂移，而漂移不會有任何錯誤訊息。
**方案 C**：把分組邏輯抽成獨立檔案讓兩邊都 import。viewer 的 app.js 是
自包含嵌進單檔 HTML 的（零外部相依是它的設計前提），做不到。

## 批次操作的實作形狀

既有 `deleteSourceDocument(driver, docId)` 內部已是
`driver.transaction()` 包住「逐表 DELETE ＋ 刪 source_documents ＋ NHI
綁定解除」。批次版**在單一 transaction 內對批次每個 docId 套用同一段
邏輯**並合計 `deleted`，而非另寫一套：

- `previewBatchRescue(driver, docIds, opts)`：合計各表 counts、
  合併 overlapWarning（任一為真即為真）、NHI 綁定判定以整批為單位計算
  （CPAP 非 NHI adapter，此路徑對 CPAP 為空操作）。
- `deleteSourceBatch(driver, docIds)`：單一 transaction，全成功或全回復。
- `reattributeSourceBatch(driver, docIds, targetProfileId)`：同上。

批次的 docIds 由檢視層依「同 adapter ＋ 同 imported_at」算出後傳入，
引擎層不重新推導批次（引擎不該知道 UI 的分組規則）。

## 驗證策略

| 組 | 純邏輯（單元測試） | 需實機 |
|----|-------------------|--------|
| 1 | 禁用詞清單同步、`app/src` 全域掃描零命中、雙份 app.js 同步 | 分頁文案目視 |
| 2 | 晚數上限的邊界（恰好 N 晚／超過 N 晚整晚剔除／筆數硬上限觸發）、`event_daily` 空與非空的呈現、按晚摺疊的分組 | 分頁互動 |
| 3 | `groupDocsByBatch` 分組、與 `groupSources` 的一致性、批次 preview 合計、批次刪除的原子性（中途失敗全回復） | 紀錄頁操作與確認面板 |

每組完成時做突變驗證（移除該組的關鍵條件，確認對應測試轉紅後自備份復原），
並確認突變確實打中待測分支——本輪走查已經出現過一次「突變沒轉紅，因為
測試根本走不到那條路」。

`imported_at` 統一寫入要驗的是**兩邊都改**：JS 與 Python 各匯入同一批
多檔來源後，`source_documents` 的 `imported_at` 在批內全等，且 parity
測試仍全綠。
