### commit 前 diff 全讀抓到的一個 spec 違反

整批合計的 `import_stats` 原本無條件寫在 `STR.edf` 那一列。但 `STR.edf`
可能是**重複檔**（第二次插卡時只有新的 DATALOG 檔是新的），此時覆寫它的
`import_stats` 會抹掉首次匯入的統計，違反 `app-import-engine`「匯入不破壞
既有資料」的白名單（該白名單只允許寫入**本次新建**的 `source_documents`
列）。已改為只在 STR 本身是新檔時才寫，並補上對應斷言。

原本的「重複匯入」測試沒抓到它，因為那個測試的全庫 dump 只比對了
`id／filename／sha256`，沒有納入 `import_stats`。dump 的欄位選得不夠寬時，
它給出的「逐位元組不變」是有範圍限制的保證。已把 `import_stats` 納入。

## 本組發現的重要事實：Phase 1 沒有血氧資料

`cpap_oximetry` 匯入後為 **0 列**。追查後確認**這是正確行為，不是缺陷**：
`SAD` 檔結構完整、record 數正確，但**全部樣本都是缺測值**，
兩個訊號都沒有任何一筆有效量測。該機型需外接血氧模組才會記錄。

影響：

- 血氧的粒度決策（逐分鐘聚合 vs 逐秒全存）在 Phase 1 是空操作，兩者都是
  0 列。該決策的價值在 Phase 2。
- UI 的睡眠期血氧圖在 Phase 1 會是空狀態，MUST 走既有的「無資料」呈現
  而不是空白區塊（第 5 組要落實）。
- 已同步更正 design D6、proposal、handoff 與 common-ground 假設 #64。

**一個驗證方法上的教訓**：先前查 SAD 缺測時問的是「有沒有樣本等於
`digMin`」，得到 0 就判斷資料正常。實際上全部樣本都落在 `< digMin`。
查缺測 MUST 用與程式相同的判準，否則驗證會給出令人安心的錯誤答案。

## 設計要點與其證據

- **整批單一交易**：缺 `profileId` 的情境驗證了連 `source_documents` 都不留。
- **每檔一列 `source_documents`**：真實素材的列數與被解析檔數相符；部分新檔
  情境驗證了增量只處理新檔。
- **`session_date` 由檔頭時刻套正午邊界推導，不取檔名日期**：素材實測全部
  session 都在正午之後、午夜之前開始，兩種取法結果相同，但午夜後就寢時檔名
  日期會與每日摘要差一天且無錯誤訊息。純函式測試涵蓋午夜後、跨月、跨年。
- **治療壓力進主要欄位，面罩／吐氣壓力進 `extra_json`**：主要欄位只放兩台
  機器共通的臨床量，不長成 ResMed 的形狀（proposal 約束）。資料不遺失，
  日後要用不必重新匯入。

## 已知限制

- CPAP 三表的 `quality_flags` 尚未納入 `qualityFlagCounts()` 的統計範圍
  （該函式目前掃指紋表與 `apple_records`），因此品質報告不會列出
  `multi_session` 的筆數。資料本身已正確寫入。
- 逐檔 `import_stats` 與整批合計分別寫在各自的 `source_documents` 列，
  報告卡的雙層呈現留待第 4 組。
