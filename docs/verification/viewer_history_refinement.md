## 組 2：呼吸事件聚合與分年定位

### 上限語意：從「最近 N 筆」改為「最近 N 晚的完整逐筆」

按筆數切會落在某一晚的中間，那晚只剩一半事件而畫面上看不出被截斷。這是正確性
問題不只是版面問題。

實測依據（對生產庫副本，2026-08-13）：

| 量 | 值 |
|---|---|
| payload 總大小 | 遠低於 `assemble.js` 的 10 MB 上限 |
| 逐筆事件 | **110 bytes/筆**（上限推算的依據） |
| 有逐筆事件的晚數 | 只佔全部有摘要的晚的一小部分（SD 卡 DATALOG 只留最近約 20 天的逐日檔，`STR.edf` 才累積長期摘要） |
| 有事件的晚：每晚筆數 | 平均與最大值均為兩位數 |

晚數最初取 90，理由是「畫面上的晚標頭不能無限長」；三層摺疊上線後那個顧慮消失，
放寬到 **365 晚**（依上面的每筆大小推算，佔上限個位數百分比），密度更高時
由 **8,000 筆**硬上限接手（不到 1 MB 為上界），剔除以整晚為單位。

### 檢視層

- 新增「每晚事件數」四條線，資料來自 `event_daily`——它早就算好塞進 payload
  卻從未被使用，而且不受任何上限影響。
- 逐筆改為**年 → 晚 → 逐筆**三層，預設全收，展開才建 DOM。摺疊起來也全部渲染
  的話，上限情境會有 8,000 個 `<tr>` 掛在頁面上；即使延遲渲染，每晚一行標頭仍
  會隨年數線性增長（十年約 3,650 行）。

### 孿生守衛的盲區（design D1 的判斷被實測推翻）

design 原寫「`payload.js` ↔ `embed.py` 這對無自動守衛」。實測只改 JS 就讓
`provider 同構` 測試轉紅，所以**有**守衛；但它有盲區：常數值分歧只在資料量觸及
較小的那個上限時才顯現，fixture 遠低於上限會全綠通過。因此仍補了常數比對守衛
（`cpap_event_limit_parity.test.mjs`），並加「有解析到兩個常數」的護欄——擋的是
兩邊同時改名導致 `undefined === undefined` 的假綠，單邊改名不需要這道也會紅。

### 邊界測試（5 條）與突變（3 次）

恰好 365 晚全帶入不標記截斷／366 晚時最舊那晚**整晚不在**／每晚 200 筆 × 50 晚
觸發筆數上限時剩下的每晚仍是完整 200 筆／完全無事件／`event_daily` 涵蓋全部夜晚。
突變：查詢改回按筆數 `LIMIT`、硬上限改為按筆數截斷、UI 不渲染每晚事件數——皆轉紅。

fixture 一開始撞到真實 schema 的 `UNIQUE(profile_id, device, start_ts, event_type)`
（每晚 200 筆時時刻重複），修正時刻產生方式後通過。硬上限測試原本硬編了 90 晚
推出來的日期並造七萬多列（3.9 秒），改為用 SQL 取實際最大日期、規模降到 50 晚
× 200 筆（0.6 秒）。

## 組 3：匯入紀錄批次摺疊與批次操作

### 批次識別的地基（common-ground #81 推翻了原假設）

原以為「同 adapter ＋同 `imported_at`」可直接作為批次識別。實測 `store.js` 的
INSERT 不帶 `imported_at`，走 schema 預設 `datetime('now')`，**每列各自取當下
時間**；實測那一批的各列時間戳相同只因插入夠快。批次一大或機器一慢就會跨秒。

**這不只影響新功能**：檢視層既有的 `groupSources` 用的正是同一個 key，所以它是
既有功能的潛在缺陷，只是還沒暴露。

修法：`registerSource` 新增選用 `importedAt`，多檔 adapter 在 transaction 內查
一次 `datetime('now')` 整批共用；傳 null 時走 `COALESCE(?, datetime('now'))`，
單檔 adapter 因此完全不用改（一批一檔，逐列時間即批次時間）。值由資料庫時鐘
產生，格式必然與既有資料一致，不必在兩種語言各自格式化。Python `db.py` 同步。

回傳的 `importedAt` 語意保持不變＝「這個檔**先前**已匯入的時間」，新插入必為
null——三個呼叫端用它判定重複檔，改成回傳剛寫入的值會讓新檔被誤判為重複。
（tasks 原本寫「新插入時回傳該值」，是錯的，apply 時修正。）

**驗證要看機制層**：只斷言 `COUNT(DISTINCT imported_at) = 1` 在插入夠快時會
假綠（逐列各自取也可能落在同一秒）。測試改為攔截 INSERT 的參數，斷言每一列都
帶了同一個非 null 時間戳且格式符合 `datetime('now')`。突變（不傳時間戳）轉紅。

### 分組邏輯的兩份實作

檢視層 `app.js` 整份包在 IIFE 內、且自包含不能 import，所以 `groupSources` 在
沙箱外取不到——「直接呼叫兩份函式比對回傳值」不可行（G1 的 S6 抓到，design D7
原方案因此改寫）。改為**共用測試向量**：`tests/helpers/batch_vector.mjs` 定義一組
輸入（同批多檔、同 adapter 不同批、單檔批次、缺統計）與期望分組，App 端直呼
`groupDocsByBatch` 斷言，檢視層放進 payload 真渲染檢查 DOM（含合計數字
事件合計＝組內各檔相加、重複略過也要合計，以及缺統計要顯示「早期匯入，
無統計」而非算成 0）。

### 批次操作

`doc_rescue` 抽出 `deleteDocIn`／`reattributeDocIn` 核心（SQLite 不支援嵌套
transaction，批次版不能呼叫單檔版 N 次），批次三函式在單一 transaction 內逐個
套用同一段邏輯。逐個套用在 NHI 語意上是自然正確的：解綁判定會隨批內前面幾筆
已刪除而變化，也就是刪到最後一份健保檔時才解綁。

原子性測試用既有 sabotaged driver 手法（第 3 次 `DELETE FROM source_documents`
拋錯），斷言 `assert.rejects` 後全庫逐位元組不變。突變（改為逐檔各自
transaction）轉紅。

## 開工後挖出的四個既有缺陷

CPAP change 新增三張資料表，卻沒有接上任何「以表清單列舉」的既有機制。實測
（非推測）後果：

| # | 位置 | 後果 |
|---|------|------|
| 1 | `DOC_DATA_TABLES` | 刪除 CPAP 來源檔 `FOREIGN KEY constraint failed` |
| 2 | `reattributeDocIn` 的表迴圈 | 改歸屬把資料留在原成員，回報「搬移 0 筆」**看似成功** |
| 3 | `PROFILE_DATA_TABLES` | 刪除含 CPAP 資料的成員同樣 FK 失敗 |
| 4 | `viewer.js` 的「有沒有資料」判定 | 只查 `encounters` ＋ `apple_records`，只有 CPAP 的成員檢視頁整片空白，payload 根本沒組裝 |

前三項都是既有 spec 的 MUST 沒被履行（「該檔全部關聯資料列」「連帶資料」）；
第四項更隱蔽——硬編在 SQL 裡而不是清單。全部只影響未發布版本（v0.5.0 沒有
cpap 表）。

修法：兩份清單各補三表（`PROFILE_DATA_TABLES` 的三表 MUST 排在
`source_documents` 之前）；apple 專用迴圈擴為 `KEY_DUP_TABLES` 五表並補三條
`KEY_MATCH`；`viewer.js` 改為沿用 `PROFILE_DATA_TABLES` 逐表 `EXISTS` 短路
（`apple_records` 有數十萬列，不能 `count(*)` 相加）。

**CPAP 的去重條件只比對鍵、不比對數值**，與 apple 兩表刻意不同：Apple 同時刻
可能有多來源不同值（要比對數值才算重複），而同一台機器同一晚的 CPAP 摘要只會
有一份，比對鍵即是匯入時的去重語意，也才符合 spec 要求的「鏡像匯入去重規則」。

**根本解**：新增 `tests/engine/table_coverage.test.mjs`，從 `DDL` 解析出每張
資料表，斷言都在兩份清單裡（含順序約束與幽靈表名檢查）。補值不能防再犯——同一輪
已經在紀錄頁踩過「四處補了、第五處沒補」。三處清單各自突變皆轉紅（突變 3 打紅
四條，因為 `seedMember` 已涵蓋 CPAP 三表，既有的成員刪除／回滾／sha256 釋放
測試也一併蓋到）。

## 藥品品項檔快取的靜默降級

`drugCachePath` 的 bundle 分支用 `exists(bundled)` 探測，該探測在 dev 模式失敗
並被 `catch` 吞成 null。後果：payload 少了 `drug_zh`，用藥頁的西藥品項全部落到
「診療項目與其他」，畫面只在說明行寫「未建快取」。改為直接
`copyFile` 到資料目錄（權限已允許），之後永遠走第一條解析路徑；失敗時把原因寫進
console 而非無聲吞掉。

實測對照：`drugCachePath` 有值時**近半數用藥**帶到 `drug_zh`，為 null 時**零筆**；
`r9`（中醫用藥）兩種情況都正常，因為它走 `section_hint` 不碰快取。

## 已知限制

- `viewer.js` 的兩個修復（空白判定、快取自動複製）與 `main.js` 的版本標示
  **沒有自動化測試**：它們依賴 Tauri API，只能實機確認。
- 時間軸的 `focus.enc` 跳轉展開哪一年，無法從外部注入 `focus`，只能實機驗
  （測試涵蓋的是同一層保護的另一半：同時只展開一年、切換年份可看到內容）。
- 批次預覽的 NHI 綁定判定取批內第一個有判定的即可。多檔批次目前只可能來自
  CPAP（健保與 Apple 都是單檔匯入），若未來出現多檔健保來源，整批解綁的判定
  需要以「排除整批」計算，那段要重新檢視。
- 批次識別的殘餘風險：兩批不同資料夾在同一秒匯入會被誤合併為一批。需要手動
  操作兩次匯入且落在同一秒，且後果僅為顯示分組，不影響資料。
- `events_total` 仍在 payload（shape 要求）但 UI 已改用晚數表達，未使用該欄位。
- `ADAPTER_LABELS`（App）與 `ADAPTER_ZH`（檢視層）是兩份標籤表、無自動守衛。
  本輪把 `resmed_edf` 統一為「CPAP（ResMed）」，但重複本身還在。
