# 驗收紀錄：schema 3→4 遷移與遷移前快照（change cpap-sleep-therapy 第 1 組）

僅記結構性結論與筆數，**不含任何個人健康數值、不列絕對日期**
（依 design D12 的個資紀律與既有 `docs/verification/*.md` 慣例）。

## 為何這一組單獨驗證

這是 v0.3 以來第一次讓既有生產庫真正跑遷移，失敗代價是資料庫打不開。
本 change 其餘各組（EDF 解析、GUI、檢視層）錯了看得見改得快，由既有測試
接住；只有這一組的失敗是不可逆的，因此驗證不放鬆。

## 自動化測試（`app/tests/store/migration_v4.test.mjs`，新增 8 項）

| 情境 | 斷言 |
|------|------|
| v3 升 v4 | 版本為 4、三表與三索引建立、新表為空、**既有各表逐位元組不變**（排序 dump 全字串比對） |
| 遷移中途中斷 | 整段回滾至 v3、三表不存在、既有資料逐位元組不變 |
| 全新庫 | 直接建到 v4，只有一筆版本紀錄（不留逐版升級痕跡） |
| 版本紀錄被清空 | 明確拋 `NoMigrationPath`，不得靜默通過 |
| MIGRATIONS[3] 形式 | 每個元素為單一語句（Python 端逐句 `cur.execute`，不走 `executescript`） |
| 快照判定純函式 | 全新庫（null）不做；落後版本才做；已最新或更新不做 |
| 快照檔名純函式 | 帶來源版本與日期，同名附序號 |
| 快照檔名拒絕污染輸入 | 非整數版本／序號、非法日期一律拋錯（該值會組進檔案路徑） |

**改寫 `initSchema` 時自行引入並修掉的一個迴歸**：把「先比較版本再遷移」
拆開後，`schema_version` 表存在但無任何列（庫被清空）的情況會落入
`null > 4`／`null === 4`／`null < 4` 全為 false 的空隙，於是靜默回傳 null 並
讓後續操作跑在缺表的庫上。原本的寫法會（以語意不精確的訊息）拋錯。
已補明確攔阻與對應測試。此問題由 commit 前的 diff 全讀發現，不是測試抓到的
（既有測試只覆蓋「有列但版本號未知」）。

既有測試同步更新：`schema_parity`（v2 庫改為逐版升至最新，並斷言 CPAP 三表
建立）、`smoke_contract`（表數 12 → 15）、`export_snapshot`（快照筆數比對
涵蓋新表）。

**突變驗證**：拆掉 `initSchema` 的交易化後，「遷移中途中斷」轉紅 1 項，
其餘 3 項不轉紅（無害對照組）。復原後與備份逐位元組相同。

測試總數 153 → **161 全綠**；`pytest` 65 全綠（含 schema parity 的 Python 側）。

## 設計要點與其證據

- **遷移整段包在單一交易內**（`schema.js` 的 `initSchema`）：未交易化時若第二
  張表建到一半中斷，庫會停在「版本已寫新值但表只建了一部分」的不一致狀態。
  證據＝突變測試（拆掉交易化即轉紅）。
- **快照用 `exportDbSnapshot`（`VACUUM INTO`）而非 `fs.copyFile`**：
  `location.js` 已記載複製前必須先關閉主庫連線（連線池握檔陷阱，見
  `g3_task0.md`），而遷移正發生在開庫流程中，庫必然開著。`VACUUM INTO`
  取單一交易視角、不中斷主庫，且產物可被既有「匯入既有資料庫檔」讀回。
  證據＝副本演練中快照維持 v3 且可重新開啟讀取。
- **快照失敗中止遷移**：`migrateWithSnapshot`（`main.js`）在快照拋錯時改拋
  帶指引的錯誤（含備份目標路徑），不靜默續行。
- **DDL 單一來源**：`CPAP_DDL` 常數同時供初始 DDL 與 `MIGRATIONS[3]` 使用，
  兩處手寫必然漂移（migration 2 即為重複語句維護的前例）。

## 已知限制

- 快照只在偵測到版本落後時產生，且不自動清除。同日多次升級會以序號累加，
  上限 100 個之後要求使用者自行整理（訊息含檔名樣式）。
- `migrateWithSnapshot` 的編排在 App 端（需 Tauri fs），node 測試只覆蓋其
  兩個純函式；整條路徑的驗證留待實機（既有慣例：App 端流程由實機演練驗收）。
