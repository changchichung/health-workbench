## 未發布：change `trend-time-axis`（已 archive）

改的是趨勢頁折線圖。起因是回報「資料多年會很擠、沒有年月選擇」，
核對後發現底下有更嚴重的正確性問題：x 軸依「第幾個有資料的日期」等距
排列，導致停止記錄的序列末點畫在繪圖區右緣看似最新（實測一條末筆距今
數百天的序列，cx=760 正好是右緣），只有 3 筆的檢驗項目被鋪滿
整個圖寬看似連續趨勢。

落地內容（全在 `app/src/viewer/assets/app.js`，同步 `src/dashboard/app.js`，
未動 CSS）：共用時間域線性映射（tMin/tMax 取區間日曆邊界，today 取
`max(generated_at, 資料最新日期)`）、時間刻度單調降級階梯、右側固定
圖例、標記兩段門檻（由繪圖寬度推導）、整頁區間選擇（近三月／近一年／
全部）＋自動預設＋單圖空狀態「看全部」、步數粒度隨區間、日期清洗。
另修既有落差：`generated_at` 在 App 端是 UTC 日期、Python 端是本地
日期（台北時區每天差八小時），新增 `engine/values.js` 的 `localDateISO`
統一。

驗收：`docs/verification/trend_time_axis_closeout.md`（生產庫唯讀副本
量測，停止記錄序列的末點 760→600、SVG 節點降幅約九成）。

**已知限制（spec 有記，非留白）**：「全部」區間下密集序列仍是雜訊帶

## 下一輪主題：`cpap-sleep-therapy`（CPAP 睡眠呼吸資料匯入 Phase 1）

新增第三類資料來源：CPAP（陽壓呼吸器）的 SD 卡原始資料。開發端可取得
兩台機器的真實素材作驗證（不進 repo／CI，已另存備份）。

**分階段策略（已拍板）**
- Phase 1（本 change）：通用 CPAP schema＋UI＋**ResMed 原生 EDF adapter**
- Phase 2：Philips 走「使用者自行以 OSCAR 匯出 CSV，App 匯入 CSV」
  （OSCAR 是 GPL-3.0，MIT 專案不得移植其碼；由使用者跑外部程式再匯入
  其輸出，授權乾淨）
- Phase 3（可選）：原生 PRS1 解析，需先取得 Apnea Board wiki 的格式
  文件（該站 Cloudflare 擋機器讀取，要使用者用瀏覽器取得）

**為何先做已停用的機型**：ResMed 素材不可再生（該機已停用、無其他備份
來源、曾遭誤刪一次）；且它走公開標準 EDF，是建立共用 schema／UI／測試
基礎最便宜的路。**但 Phase 1 單獨存在沒有持續迴圈**（仍在產生新資料的
是 Philips），因此 schema MUST 以兩台機器共通的臨床量設計，不得長成
ResMed 欄位的形狀，否則 Phase 2 會被迫遷移。

**格式事實（2026-08-12 重驗；素材本身不進 repo，數量級細節留在本機）**
- ResMed（`~/Downloads/resmed`）：`STR.edf` 為 28 訊號、**每 record 一天**
  （`dur=86400`）、含 AHI/AI/OAI/CAI/UAI/HI、Leak 95、Mask Pres 95、
  Mask Dur；`DATALOG` 是平的一層，只有 20 晚細節（PLD 11 訊號／SAD 血氧
  脈搏／EVE 事件／BRP 波形）。**四個必記的坑**：(a) record 起始為正午
  12:00，`Mask On/Off` 是自正午起的分鐘數（跨午夜者 >720）；(b) 未使用日
  以哨兵值佔位（原始數位值 **-1**），判定要用 **`dig < digmin`**（不是
  `== digmin`！digmin 多半是 0 或正數，那些是合法量測：實測有數百天的
  UAI 真的是 0、同量級天數的最低壓力真的等於 digmin。寫成 `== digmin` 會同時
  漏掉全部缺測日並誤刪數百天真資料）；也不可用 phys 值比對（scale 不同，
  會是 -1／-0.02／-0.1）；不濾會畫出一整片假點；(c) EDF label 欄位僅 16 字元，標籤
  被截斷成 `Therapy Pres Me`／`Therapy Pres Ma`；(d) EVE 事件有**五類**：
  `Obstructive Apnea`／`Central Apnea`／`Hypopnea`／未分類 `Apnea`／
  非事件的 `Recording starts`，漏掉未分類 `Apnea` 會使 AI 與分項對不攏。
  另：`SAD` 是 **1Hz 逐秒**（非逐分鐘），`AHI = AI + HI` 全數成立。
  **(e) 這台機器沒有血氧資料**：`SAD` 檔結構完整但全部樣本 100%
  都是缺測值（需外接血氧模組，這台從未接過）。血氧表在 Phase 1 匯入後
  為空，UI 要走空狀態。查缺測時要用與程式相同的判準（`< digmin`），
  先前查「== digmin」得 0 而誤以為資料正常。
- Philips：數千檔／數十 MB，持續產生中（與 ResMed
  的涵蓋期重疊約五個月，故 schema 去重鍵必須能區分裝置），序號目錄下
  P0-P4，`.001` 摘要／`.002` 事件／`.005` 波形。
  專有格式，唯一完整實作是 GPL-3.0 的 OSCAR，寬鬆授權的解析器幾乎不存在。

**common-ground 裁示（assumptions #53-#69，在 `~/.claude/common-ground/myhealthbank/`）**
- 粒度＝每日摘要＋呼吸事件＋血氧脈搏**逐分鐘聚合**（SAD 實為 1Hz，
  逐秒原始值不入庫：數十晚兩訊號就達數十萬列，等於再塞一個現有生產庫，
  且 Phase 2 會達千萬列等級；改存每分鐘 SpO2 最低／平均與脈搏
  平均／最高，降到千列量級）；PLD 逐分鐘 11 訊號與 BRP 波形不入庫
- 血氧＝CPAP 與 Apple 都存、以來源區分同圖疊線（沿用體重多來源模式）
- 驗證＝自產合成 EDF fixture 數值斷言＋真實檔案人工對帳一次，
  **明示豁免「每個 adapter 都有 Python oracle 差分對帳」紀律**，
  Python 端只同步 DDL
- UI＝**獨立分頁放完整內容＋趨勢頁放簡單混合對照**，總覽加一張卡
- 去重鍵已定案（原 OPEN #60）＝**每檔一列 `source_documents`**（STR.edf
  與每個 DATALOG 檔各一列）：沿用既有 `UNIQUE(sha256)`，下次插卡只有新檔
  被處理，且天然滿足「來源追溯到原始檔案位置」。代價＝報告卡改批次呈現。
  **無殘留未解 OPEN**

**design 必須處理的三個難點**
1. **多檔來源**（最大架構改動，比 EDF 解析本身大）：`app/src/ui/import_flow.js`
   的 `offerFile` 一次一檔（資料夾會被解析成單一檔案，Apple 情境），
   ResMed 是整個 SD 卡資料夾（`STR.edf` 加 DATALOG 上百檔），adapter
   介面與資料夾處理都要擴充。
2. **schema 3→4**：`MIGRATIONS` 前向遷移機制與範例既有；schema parity
   測試強制 `src/store/schema.py` 同步 DDL 與 MIGRATIONS（「Python CLI
   功能凍結」不豁免 DDL）。
3. **遷移風險**：這是 v0.3 以來第一次讓既有生產庫真正跑遷移（實測規模
   數十萬列／百 MB 量級、schema v3），失敗代價是資料庫打不開，design 要明確
   處理失敗與回復路徑。

**產品定位**：加第三類來源會改變 README 定位（現為「健保存摺＋Apple
健康」），README 與倉庫描述要同步。AHI 等臨床指標只顯示不解讀（既有
禁用詞守衛已涵蓋這類措辭）。

## 本輪工程教訓

前一輪的教訓仍適用（差分對帳護欄兩度救場、sqlx 參數綁定、Python↔JS
逐位元組等價的坑）。本輪新增四條，其中三條已寫進專案 memory：

- **原型實驗要對準結論**：用「標記畫不畫」的原型推導「時間桶聚合的
  可讀性收益接近零」是換題——三個變體畫的是同一條折線。假結論寫進
  SSOT 會讓下一輪把該做的事永遠擋在門外。QA 稽核補做了缺失的變體，
  實測聚合確實把雜訊帶變成可讀的線；已更正 design 與 proposal 並註明
  「不要把那句話當已驗證事實」。
- **`spectra archive` 會吃掉 `@trace`**：delta 覆蓋 requirement 時連
  溯源註記一起蓋，已連兩輪踩到。做法＝delta 不手寫 trace、archive 前
  記下各 spec 的 requirement／trace 數、archive 後補回（MODIFIED 的
  trace 保留既有驗證文件指標並附加本輪 closeout）。
- **QA 稽核要指定盲點方向並用突變測試驗斷言**：明確要求稽核查「已知
  限制是否掩蓋未完成／砍範圍理由成不成立／有無無聲退化」，三項全部
  命中真問題（總覽卡標記歸零且該卡無區間可切、假結論、最顯眼的血壓
  數字卡沒修）。稽核另用突變證明三處斷言毫無效力（門檻改 5000／步數
  永遠月平均／截斷改 99 都不轉紅）。
- **public repo 的個資把關要涵蓋敘述層，不只資料層**：v0.5.0 轉 public
  前檢查的是資料檔與截圖，但 SDD 文件的 Why 段天生要寫「為什麼做這個
  功能」，於是明確診斷敘述、個人量測時間軸（某序列末筆的絕對日期＋
  之後停止）被推上公開網路。2026-08-12 全面中性化改寫 HEAD：技術事實
  （工程量測、測試常數）全部保留，去掉的是「這是誰的資料」的指向與
  可組成健康時間軸的日期組合；序列改以類型代稱（「已停止序列（血壓
  類）」）。**規則：任何要進 repo 的文件，個人健康敘述一律寫成不指向
  特定個人的功能理由；驗證紀錄用相對跨度不用絕對日期。**
- **同一個門控卡兩次要上報，不要硬幹**：`trend-time-axis` 的 G1 兩輪
  都 BLOCKED，照 default-deny 條款交使用者裁示，使用者選「進 apply 讓
  G3 接手」，結果實作順利。文件打磨的邊際效益會下降，而這個 change
  是純檢視層、有真渲染測試護欄、錯了看得見也改得快。
