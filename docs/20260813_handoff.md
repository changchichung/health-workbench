## 流程上的裁示：門控強度對準風險

本輪未走完整 SDD 門控。裁示內容與理由：

- **跳過 G1 的 sub-agent 審查**：六項 Self-Review 已抓到三個真問題
  （`copyFile` 用錯、雙軸圖會壓平序列、`Mask On` 十槽位遺漏），再派一輪
  審查的邊際效益低。
- **specs delta 延到 apply 完成後撰寫**，依實際落地行為而非想像。
- **QA 三連縮為一次現實檢核**，並指定盲點方向（限制措辭是否掩蓋未完成／
  砍範圍理由／無聲退化）。
- **只有第 1 組（schema 遷移）驗證不放鬆**：那是唯一不可逆的失敗。

這個裁示的背景是「規劃太久」：proposal 早上寫完，到動第一行程式跨了
十幾個小時。事後看，本輪最貴的錯誤（缺測判準）在 design 裡寫了三處且
彼此一致，卻在寫測試的第一天就露餡 — 那類決定不值得在文件階段反覆打磨。

## 本輪最貴的三個教訓

1. **design 寫得篤定不代表正確**：缺測判定 `dig == digMin` 在 design 三處
   一致，實際上**雙向都錯**（漏掉全部缺測日＋誤刪數百天合法 0 值）。
   縮放公式在該條件下恆等於 `physMin`，代一組數字就會發現。
   **規則：design 裡的判準／公式／閾值，寫進去前先代真實數字驗算。**
2. **驗證要用與程式相同的判準**：查血氧缺測時問「有沒有樣本等於 `digMin`」
   得到 0 就判斷資料正常，實際上全部落在 `< digMin`。問錯問題會得到一個
   令人安心的錯誤答案。
3. **自己剛訂的紀律最容易自己違反**：design D10 否決雙軸圖的理由是單一
   y 軸會壓平小數量級序列；寫睡眠分頁時我又把漏氣與壓力放同一張圖。
   commit 前的 diff 全讀抓到。

另有一條在前一輪已記：**public repo 的個資把關要涵蓋敘述層**
（SDD 文件的 Why 段天生會寫個人情境，資料層檢查抓不到散文）。

第一次真正遷移。pytest 65 → 67。

## archive 與 trace

`spectra archive` 如既往吃掉 `@trace`（**連三輪**）。本輪照既有做法處理：
archive 前記下各 spec 的 requirement／trace 數，archive 後逐一補回，
MODIFIED 的保留既有驗證文件指標並附加本輪 closeout。

補回後 12 個 spec 全部 `req = trace`（`app-viewer` 10 → 14、
`health-database` 6 → 7、`app-import-engine` 8 → 9、新增 `cpap-therapy` 7）。
