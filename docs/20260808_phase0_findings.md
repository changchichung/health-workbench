# Phase 0 格式探索發現（2026-08-08）

依據：真實健康存摺醫療類下載檔（JSON + XML，1150808 申請）與官方格式說明
`docs/specs/IHK_JSON_J2.pdf`（修訂 112.05.15）、`IHK_XML_X2.pdf`。

## 格式事實

- 下載檔為 UTF-8 with BOM、CRLF。JSON 與 XML 是**同一套代碼 schema**（14 合 1），
  結構：`myhealthbank.bdata` 下 `b1.1`（遮罩身分證）、`b1.2`（申請日期）+ r1～r14。
- 節區代碼大小寫不一致：r1～r11 小寫、R12～R14 大寫，parser 需正規化。
- 官方下載檔**自帶身分證遮罩**（A12345****（示意）），個資風險低於預期。
- 「無資料」節區以 `[{"rN": "無資料"}]` 佔位，r0 是聲明書 HTML 文字。
- 節區對照：r1 西醫門診（含 r1_1 醫囑）、r2 住院、r3 牙醫（含 r3_1，多牙位欄）、
  r4 過敏、r5 器捐/安寧、r6 預防接種、r7 檢驗檢查、r8 影像病理報告、
  r9 中醫門診（含 r9_1）、r10 成人預防保健（身高體重血壓在此）、r11 癌篩、
  r12–r14 糖尿病/腎病/BC 肝追蹤。
- 日期為西元 YYYYMMDD 字串；藥局交付調劑紀錄的 r1.5 就醫日期為空、
  改填 r1.6 交付調劑日期、就醫序號為 XXXX。
- 資料回溯：本批就醫紀錄約 3 年（2023-08 ～ 2026-08），證實滾動視窗假設。
  → 跨次下載累積合併是核心價值，不是 nice-to-have。

## JSON vs XML 等價性實測（2026-08-08，逐筆逐欄比對）

**不等價，以 JSON 為主。** 差異四項：
1. **XML 缺 r9～r14**（中醫、成健、癌篩、三項追蹤）。XML spec X2 明載 14 合 1，
   但實際下載檔只到 r8 且結尾完整（非下載中斷），是健保署輸出端缺漏。
2. r8 影像病理報告：JSON 版換行被移除、XML 版保留（長報告可讀性 XML 較好）。
3. 藥品名稱引號：JSON 把 `"永勝"` 轉成 `'永勝'`（避免跳脫的置換），XML 保留原字元。
4. 紀錄排序不同（XML 藥局調劑在前）、空欄位表示不同（XML 空標籤=None、JSON=""）。
   排序與空值正規化後，r1/r3/r6/r7 內容完全相等。
→ 策略：pipeline 只依賴 JSON；XML 可選，僅用於補 r8 報告換行與藥名原字元。
比對工具：`phase0/compare_json_xml.py`。

## 資料回溯範圍（實測 + 官方說明）

- 就醫類（西醫/中醫/牙醫/用藥/檢驗/影像）：登入日前 2 日起**近 3 年**，
  這是健康存摺系統對所有人的限制，非帳戶等級差異。
- 但**疫苗接種（r6）與成健（r10）實測回溯超過 3 年**，
  部分類別回溯更長，各節區範圍需分開對待。
- 3 年以前的就醫紀錄：健保署有付費申請管道（保險人提供資料申請書，
  簡易格式每人次 300 元、詳細格式按工時計費），但取得的是申報資料格式，
  不是健康存摺 14 合 1 格式，需另寫 parser 才能匯入。

## 本批資料量（單人 3 年）

七類節區（就醫事件、用藥明細、檢驗結果、影像病理報告、疫苗、成健、癌篩）
的筆數全部落在**數十至數百**的量級，合計不到一千筆。
量級極小，SQLite 毫無壓力；IndexedDB 容量疑慮可從規劃書刪除。
（各節區的實際筆數不記於此：此 repo 公開，就醫科別分佈與各類紀錄數
合起來構成可辨識的個人健康資訊。）

## 資料品質發現

1. **跨院所檢驗名稱不一致**：同項目有 Hb/HB、Lym/Lym.、eGFR 三種變體，
   `test_name_normalized` 是剛性需求。
2. 檢驗結果值 65/68 可直接轉數值，3 筆為文字型結果；參考值格式雜亂
   （有的含性別年齡分段長文字）。
3. 每個檢驗項目在 3 年內通常只有 2 筆 → 單次下載畫不出趨勢，
   趨勢價值依賴長期累積。
4. 體重身高只在成健做過的那次有（r10，本批 1 筆）→ 規劃書「使用者手動補充
   家用量測」不是加分項，是體重趨勢功能成立的前提。
5. r8 影像病理的 r8.10 是長文字報告（X(12000)），適合全文搜尋不適合結構化。

## Phase 0 原型（phase0/）

- `fieldmap.py` 官方代碼→中文欄位對照（r10 部分欄名待逐字核對原 PDF）
- `parse_mhb.py` JSON → SQLite（encounters/medications/lab_results/reports/
  immunizations/body_measurements/cancer_screenings + source 追溯欄位）
- `gen_report.py` → `output/report.html` 本機報告（月度就醫堆疊圖、
  身體數值 tiles、檢驗前次→最新變化表、最近就醫表）
- 驗證：重跑兩次結果一致；醫囑明細對帳 323(r1_1+r3_1)+63(r9_1)=386 吻合；
  三查詢（依類型統計就醫、依醫囑統計用藥、檢驗數值分布）通過。

## 多來源擴充：Apple Health 實測（2026-08-08）

方向拍板：產品定位從「健保存摺分析」擴大為**多來源個人健康資料工作台**，
使用者可自行加入健保以外的資料來源。第一個驗證來源是 Apple 健康匯出。

- 匯出結構：`apple_health_export/輸出.xml`（百 MB 量級，中文檔名）、`export_cda.xml`、
  `workout-routes/*.gpx`。主檔需 iterparse 串流解析。
- 本批數十種 Record 型別共數十萬筆。健康相關（入庫）：體重、血壓、
  BMI/體脂/除脂體重、心率、睡眠等 → `apple_records` 表，佔比不到一成。
  活動類（步數/步態/能量）佔絕大多數，Phase 0 不入庫。
- **Apple 資料正好補上健保缺口**：健保的體重只有成健那寥寥數筆，Apple 則有
  跨年度的體重與血壓連續量測，體重趨勢功能因此成立。
- 髒資料案例（quality_flags 教材）：`1970-01-01/01-02` epoch 佔位日期、
  體重離群值（低到不可能是成人體重，量測失敗或他人使用）、體脂率存小數
  （0.25=25%）、匯出檔內部重複（手錶＋手機雙上報）。

## Apple Health 第二輪（2026-08-08 拍板：活動類全納入）

- 產品願景確認：**全面性檢視自己的健康**（就醫用藥 + 檢驗 + 身體數值 +
  活動生活型態，單一總覽）。
- 活動類十餘種型別全數入庫（步數/距離/能量/步態/飲食/耳機音量等），
  數十萬筆於個位數秒內完成，DB 百 MB 量級，冪等去重仍有效；另建
  `apple_workouts`。
- **Apple 資料起點 = 各裝置的使用起點**，不同類別相差數年（手機、體重計、
  手錶、血壓計陸續加入）。這是趨勢圖必須按時間定位而非按索引等距排列的
  根本原因：各序列的起訖天然不齊。
  export_cda.xml 同樣 2019 起，無更早資料。「好轻」App 的 1970 epoch
  批次實為近期量測（值域與現況吻合），是時間戳損壞不是老資料。
- **步數重複計數陷阱**：iPhone 與 Watch 同時記步，直接加總會高估；
  處理方式＝每日各來源分別加總後取最大值，再聚合。

## 檢驗/用藥解讀的可引用公開資料源（2026-08-08 調查）

原則不變：工具只「引用與連結」，不自行下醫療判斷；每則解釋標來源與日期。
- 檢驗解讀：國健署成人預防保健專區（hpa.gov.tw，成健項目官方衛教）、
  各大醫院公開檢驗手冊/衛教頁（如成大、台大檢醫部）。無現成結構化
  open data，MVP 需自建 knowledge/ 對照表（項目 → 說明 + 來源 URL + 日期）。
- 藥品：食藥署藥品許可證資料庫（info.fda.gov.tw）與仿單查詢平台
  （mcp.fda.gov.tw，有批次訂閱）、健保用藥品項查詢（info.nhi.gov.tw
  INAE3000）、政府資料開放平臺 data.gov.tw 藥物資料集。健保存摺的
  醫囑代碼（10 碼健保藥品代碼＋序號格式）前段即健保藥品代碼，可與上述資料庫 join。

## Parser 架構決策（2026-08-08 確認：每來源一個獨立 adapter）

每個資料來源 = 一個版本化 parser 模組，共同輸出內部正規化 schema
（規劃書 §6.2/§8.2 的落實）。新增來源或來源改版只動對應模組。

現成工具調查：
- **Apple Health 有現成**：[dogsheep/healthkit-to-sqlite](https://github.com/dogsheep/healthkit-to-sqlite)
  （Simon Willison，PyPI v1.0.1，export.zip → SQLite）、
  [apple-health-parser](https://github.com/alxdrcirilo/apple-health-parser)（解析+繪圖）。
  評估後**維持自寫**（phase0/parse_apple_health.py，~130 行、個位數秒處理數十萬筆）：
  現成工具是全量傾倒，沒有冪等合併、quality_flags、來源別單位修正
  （好轻體脂率存 0.255 卻標 %）這些我們的核心需求；留 healthkit-to-sqlite
  作交叉驗證參照。GPX 路線未來用 gpxpy；export_cda.xml 內容與輸出.xml
  重複，跳過。
- **健保存摺沒有現成**（GitHub 全站僅 5 個玩具 repo）：自寫的
  parse_mhb.py 就是第一個，這是護城河不是負債。

Apple 來源異質性實測：單一匯出檔內有 9 個 sourceName（iPhone/Watch、
好轻、WoFit、Myzone、Strava、MyFitnessPal…），單位與品質各異，
**來源別正規化規則表**是 adapter 層必要設計。

## 跨批次累加合併（規格硬需求，已原型驗證）

使用者會定期（如每月）重新下載/匯出，資料必須可比對累加：
- `apple_records` 以 (type, start_ts, end_ts, source_name, value) 自然鍵
  UNIQUE + INSERT OR IGNORE，實測同檔二次匯入 inserted=0（冪等）。
- 健保側自然鍵候選：(醫事機構代碼, 就醫日期, 健保卡就醫序號) + 節區型別；
  藥局調劑（序號 XXXX）需含交付調劑日期。MVP 需正式設計。
- Apple 匯出每次都是全量歷史，健保是 3 年滾動視窗：合併語意不同
  （前者天然冪等、後者是視窗接續），schema 要分別處理。

## 規劃書修訂建議

- §5.1.A 去重：升級為「跨批次時間視窗重疊合併」，這是核心差異化。
- §9/§12：刪除 IndexedDB 容量、iPad 效能等假議題；SQLite 定案。
- §6.3：doc-cleaner 僅在純 PDF 內容才需要；結構化 JSON 直接專用 parser。
- 尚未驗證：XML parser（同 schema，優先度低）、其他資料類別（健保卡狀況等
  非醫療類下載）、不同帳戶狀態下的格式差異。
